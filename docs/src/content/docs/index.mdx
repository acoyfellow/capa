## How it works

<ol class="capa-flow not-content">
  <li>
    <span class="capa-flow__step">1</span>
    <h3>The provider publishes a spec</h3>
    <code class="capa-flow__artifact">POST /v1/payment_intents</code>
  </li>
  <li>
    <span class="capa-flow__step">2</span>
    <h3>capa generates a typed method</h3>
    <code class="capa-flow__artifact">paymentIntents.create(body)</code>
  </li>
  <li>
    <span class="capa-flow__step">3</span>
    <h3>You deploy it to your account</h3>
    <code class="capa-flow__artifact">cf deploy</code>
  </li>
  <li>
    <span class="capa-flow__step">4</span>
    <h3>Your Worker or your agent calls it</h3>
    <code class="capa-flow__artifact">env.STRIPE.paymentIntents.create(...)</code>
  </li>
</ol>

<p class="capa-flow__loop not-content">
  <span class="capa-flow__loop-mark" aria-hidden="true">↻</span>
  <span>When the provider changes the spec, a weekly job regenerates the binding and opens a pull request.</span>
</p>

## Every call returns evidence

The evidence record says what capa sent, what came back, and which checks passed. Log it, show it, or ignore it.

```ts
{
  operationId: "PostPaymentIntents",
  act: {
    request: { method: "POST", url: "https://api.stripe.com/v1/payment_intents" },
    status: 200,
  },
  assert: [{ kind: "httpStatus", expected: "2xx", actual: 200, passed: true }],
  verdict: "pass",
}
```

## Quick start

Deploy a capability from the [catalog](/catalog/), set its key, then bind it from your Worker.

```bash
cd capabilities/stripe
cf migrate && cf deploy
cf workers secrets update STRIPE_API_KEY --worker capa-stripe --type secret_text
```

```ts title="cloudflare.config.ts"
env: {
  STRIPE: bindings.worker({ worker: "capa-stripe", exportName: "StripeCapability" }),
}
```

Using Wrangler? The [tutorial](/tutorial/) shows both.
